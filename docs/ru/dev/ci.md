# CI и релизы

Всё, что работает на GitHub Actions, и как выпускается релиз. Тест проверяет, что каждая задача
`.github/workflows/ci.yml` и `site.yml` есть в этих таблицах на обоих языках.

## `ci.yml`: на каждый пуш

Пуш в `main` запускает всё: около часа вместе со сборками, поэтому пушить пачками, а не после каждой мелочи.
Коммит с `[skip ci]` в сообщении не запускает ничего.

| задача | когда | что делает |
|---|---|---|
| `lint` | каждый пуш и PR | `ruff check .` (длина строки 100) |
| `security` | каждый пуш и PR | код синхронизации смотрит в интернет: `bandit` и правила bandit в ruff по `syncserver/` и `fedtail/core/sync`, его тесты безопасности, на Python 3.11 и 3.13 |
| `audit` | каждый пуш и PR | известные уязвимости в том, на чём работает fedtail (`pip-audit`): только предупреждения, новая CVE у зависимости релиз не держит |
| `test` | каждый пуш и PR | все тесты на Python 3.11, 3.12 и 3.13 с Qt из pip, без экрана; потом fedtail ставится как пакет и запускается |
| `debian` | каждый пуш и PR | все тесты на Debian 13 с Qt и GTK 4 из apt, под Xvfb — настоящая цель |
| `windows` | каждый пуш и PR | все тесты на Windows с Qt из pip (docs/ru/dev/windows.md использует те же пакеты и команду, тест проверяет) |
| `windows-build` | пуш в `main` | `fedtail.exe` одним файлом (PyInstaller, `packaging/build.py`), один раз запускается |
| `linux-build` | пуш в `main` | `fedtail` для Linux одним файлом, собирается на Debian 12, чтобы работал и на старых системах |
| `deb` | каждый пуш и PR | `.deb` для Debian 13 (`packaging/deb.py`), ставится через apt и запускается |
| `screenshots` | вручную (Actions → CI → Run workflow), только `main` | каждая тема рисуется с выдуманными данными, PNG принудительно пушатся в ветку `screenshots` |
| `release` | пуш в `main`, когда всё выше зелёное | если в `fedtail/__init__.py` версия релиза, у которой ещё нет тега: ставит на коммит тег `vX.Y.Z`, публикует релиз на GitHub с разделом CHANGELOG как заметками и тремя файлами и дёргает deploy hook сайта |

Когда тест падает, `.github/annotate.py` превращает падения в аннотации прогона (журналы задач
не всегда можно скачать).

## `site.yml`: сайт

| задача | когда | что делает |
|---|---|---|
| `rebuild` | каждую ночь в 05:37 по Тбилиси и вручную | зовёт deploy hook сайта (секрет `SITE_DEPLOY_HOOK` или `DOCS_UPDATE`), чтобы «что будет» не отставало от `main` |

Сайт живёт в своём репозитории и собирается из этого: доки последнего релиза, доки разработчика
из `main`, ссылки на файлы релиза. Релиз пересобирает его сразу.

## Как выпустить релиз

1. В разделе `## X.Y.Z — in progress` в `CHANGELOG.md` есть всё, что пользователь заметит со времени прошлого релиза.
2. Одним коммитом: в `fedtail/__init__.py` — `X.Y.Z`, заголовок CHANGELOG становится `## X.Y.Z — <дата>`,
   у пришедших в нём возможностей в `docs/src/features/` стоит `since = "X.Y.Z"`, `python3 tools/docs_build.py`.
3. Пуш. Когда CI зелёный, задача `release` ставит тег и публикует; сайт подтягивается.
4. Сразу после: поднять до `X.Y+1.0.dev0` с новым разделом `## X.Y+1.0 — in progress`.

Релизы выпускаются только по слову автора.
