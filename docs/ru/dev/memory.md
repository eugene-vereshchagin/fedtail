# Как облегчить fedtail

Статус: **шаг 0 (стенд) сделан**, базовая линия ниже; 28 окт 2026. План — автора.

## Зачем

Замер на ноутбуке автора (Qt на KDE, `python3 -m fedtail`, открыт долго): USS 484 МБ,
PSS 516 МБ, RSS 656 МБ. Это не утечка — ночная самопроверка растёт меньше чем на 10 МБ за
ночь, — это штатный объём собственных данных fedtail, так что худеть надо архитектурно.
Переписывать на другой язык не будем: чистый интерпретатор с PySide6 — 100–150 МБ, остальное
наше.

Цель: **150–250 МБ USS** в том же сценарии и заметно более шустрая лента.

## Принципы

* Один системный подход для всего кода и всех интерфейсов (Qt, GTK, терминал, веб,
  Android) — никаких правок под одну платформу.
* Ядро решает, что лежит в памяти; интерфейс получает только то, что видно.
* Сначала замер, потом правки; каждая правка подтверждается цифрами стенда.
* Пачками: CI не гонять после каждой правки; для проверки автором — пуш с `[skip ci]` и
  явное «делай pull».
* Релиз — только по слову автора.
* Доки разработчика — сразу на двух языках; список фич и справочник опций — тоже.

## Шаги

| шаг | что | статус |
|---|---|---|
| 0 | **Стенд**: синтетические сутки — 10 000 постов, 20 лент по правилам, картинки, сутки опроса; память по частям (посты, ленты, кэш картинок, виджеты интерфейса, модули; C++-часть Qt — через размеры кэшей и число объектов, tracemalloc её не видит); тайминги — холодный старт до первой ленты, открытие ленты, прокрутка 1000 постов, применение правил лент; в dev-сборке эти цифры в логе каждые несколько минут; цифры первого прогона — здесь, как базовая линия | сделан: базовая линия ниже |

| 2 | **Компактные объекты вместо сырого JSON**: JSON сервера — только в SQLite; в памяти лёгкие структуры с полями для показа (`__slots__` или msgspec Struct, если пакет есть в Debian); разбор в `protocols/` сразу в них; повторяющиеся строки (URL аккаунтов, серверы, коды языков) интернировать | измерено, отложено: самое большее ~25 МБ из 61 у ядра (29.10) |
| 3 | **Ленты считает база**: правила лент компилируются в SQL (WHERE + ORDER + LIMIT) с нужными индексами, вместо загрузки постов в Python для фильтрации; атомы, которые SQL не выразит, считаются при сохранении поста и хранятся колонками (язык, тип события, мой или чужой, уже видел…); EXPLAIN QUERY PLAN проверен для всех наборов лент; бюджет базы около 1 ГБ текста в год соблюдается | измерено, отложено: самое большее ~25 МБ из 61 у ядра (29.10) |
| 4 | **В памяти только видимое**: «окно ленты» в ядре — интерфейс просит диапазон вокруг курсора (скажем, 50 постов), ядро отдаёт и держит небольшой буфер вокруг; неоткрытые ленты не загружены; счётчики непрочитанного — COUNT в базе; «где остановился» — курсор в базе, а не загруженная лента; один API для всех интерфейсов и Android | измерено, отложено: самое большее ~25 МБ из 61 у ядра (29.10) |
| 5 | **Интерфейсы без виджета на пост**: Qt — QListView / QAbstractListModel и рисующий делегат; GTK — Gtk.ListView с моделью и переиспользуемыми строками; веб, терминал, Android — то же окно, дорисовка при прокрутке; высоты строк кэшируются, раскладка текста без нужды не пересчитывается | в Qt сделано: `qt/feedview.py` строит только карточки в пределах экрана от экрана (остальные — места по своей высоте); карточки держат только ленты, открытые последними (`ui.keep_hidden_lanes`). GTK — своё окно карточек, как было |
| 6 | **Картинки и медиа**: декодируются сразу в размер показа (Qt: QImageReader.setScaledSize), полный размер — только при открытии; один кэш картинок с лимитом в МБ (опция, разумное значение по умолчанию), LRU; миниатюры кэшируются на диск; медиа вне экрана не декодируются; видео — по-прежнему только превью | частично: `media.image_cache_mb` (64 МБ по умолчанию с 0.22, измерено), `image_disk_mb`, `image_decode` |
| 7 | **Ленивый старт**: тяжёлые модули (определение языка, орфография, звук, всё редкое) — при первом использовании; первой рисуется заглушка с опоссумом, потом открытая лента, остальное в фоне; всё тяжёлое (разбор, запросы, определение языка, правила лент) — вне GUI-потока | частично: заглушка первой (0.22) |
| 8 | **Бюджеты как тесты**: стенд шага 0 — тест с потолками памяти и времени (старт, открытие ленты, прокрутка); превышение — тест падает, чтобы лёгкость не расползлась обратно с новыми фичами; гонять в полном CI, не на каждую мелочь | сделано: `tests/test_budgets.py` (`FEDTAIL_BUDGETS=1`), задание `budgets` в CI — релиз ждёт его; потолки на четверть выше цифр 28.10 |
| 9 | **Только если 1–8 мало**: горячие вычислительные куски по профилю — на Rust через PyO3, не трогая архитектуру ядра и интерфейсов | — |

Порядок: 0 → 1 → … → 8, после каждого шага — стенд и сравнение с базовой линией ниже; после
всего — проверка, что интерфейсы на всех платформах не разошлись (`tools/parity.py`,
`tools/behaviour.py`).

## Стенд

`tools/membench.py` — без сети, ваше ничего не трогает:

```sh
python3 tools/membench.py                  # ядро и общий слой
python3 tools/membench.py --ui qt          # и окно Qt (offscreen)
python3 tools/membench.py --trace          # где память Python, по пакетам (медленнее)
python3 tools/membench.py --json out.json --md out.md
```

Сценарий: поддельный сервер (`tests/fakes.py`) с `--posts` постами в Home (картинка в каждом
четвёртом, ответы, упоминания, Local тоже наполнена, лайки и подписки для Активности), база
заполнена как после нескольких дней опроса, свой набор лент fedtail плюс свои ленты до
`--lanes`, новый старт над этой базой, потом `--hours` опроса, по дюжине новых постов каждые
пять минут.

Что говорит: USS / PSS / RSS (`/proc/self/smaps_rollup`), с `--trace` — доля Python по пакетам;
счётчики ядра (`Core.diag_stats`); с `--ui qt` — число виджетов и кэш картинок (`--ui qt`
сперва кладёт в дисковый кэш настоящий JPEG каждой картинки и аватарки поддельного сервера, как
после нескольких дней чтения, — окно разжимает и держит их, как в жизни; `--image-mb N` задаёт
`media.image_cache_mb`). Время: холодный
старт (ядро, подключение, первый круг), первая лента, открытие всех лент и самая медленная из
них, правила заново, сутки опроса, и с `--ui qt` — прокрутка Home на 1000 постов.

Dev-сборка пишет USS и PSS в лог с каждой строкой статистики (`diag.smaps`, каждые
`debug.stats_minutes`).

## Базовая линия

Первый полный прогон, 28 окт 2026 (`python3 tools/membench.py --ui qt`: 10 000 постов, 20 лент,
из них видно 19, 24 ч; Python 3.13, два ядра облака, Qt offscreen; ни одна картинка не
скачалась — адреса поддельного сервера никуда не ведут, — так что кэш картинок здесь пуст):

| память | МБ |
|---|---|
| USS | 453,3 |
| PSS | 483,8 |
| RSS | 516,3 |

На ноутбуке автора было USS 484 МБ: стенд повторяет беду и без картинок — она в наших
структурах, а не только в изображениях (картинки появились на стенде позже — см. ниже: их доля
тоже велика).

| время | мс |
|---|---|
| холодный старт: ядро, подключение, первый круг | 1935 |
| первая лента (Дом) собрана | 49 |
| окно Qt открыто, Дом нарисован | 2113 |
| открыть все ленты (19) | 12 689 |
| самая медленная лента | 1819 |
| правила лент заново | 1319 |
| сутки опроса (288 кругов) | 195 679 |
| прокрутка Дома на 1000 постов | 396 |

Счётчики в конце: 13 457 статусов и 15 656 элементов в базе (32,6 МБ на диске), 294 031
объект Python (gc), 518 модулей, **14 497 виджетов Qt** — цель шага 5; каждая лента держит
свою разобранную копию каждого своего поста (`Core.lane_entries` → `json.loads` на ленту) —
цель шага 1.

Что говорят цифры, три прогона спустя (28 окт):

* **Собственные объекты Python — малая часть.** С `--trace` (2 ч опроса) tracemalloc видит
  около 95 МБ выделений Python при USS 517 МБ: ядро 18, питоновская часть слоя Qt 20, общий
  слой 4,5, json и прочее — остальное. Основное — C++-сторона Qt: виджеты, раскладка их
  текста и стили.
* **Освобождённая память остаётся в процессе, пока её не вернуть.** `--ui qt --hours 2`:
  USS 349 МБ после обхода всех лент; скрытые ленты выгружены (как делает
  `ui.unload_hidden_minutes` через 10 минут) — 854 виджета из 9382, а всё те же 349 МБ;
  после `malloc_trim(0)` из glibc — **193,5 МБ**. Работающий fedtail возвращает память каждые
  `debug.stats_minutes` (`diag.trim_memory`), так что с жизнью сравнивать надо последнее
  число; стенд печатает все три.
* **Шаг 1 на одном ядре** (`--hours 2`, без окна): USS 110,3 → 102,5 МБ, открыть все ленты
  656 → 362 мс, два часа опроса 9,2 → 5,4 с (ни одна лента не разбирает пост, уже разобранный
  другой).

Так что для ядра порядок плана верен, а вес окна — в карточках (шаг 5): каждая карточка —
десятки виджетов.

* **Шаг 1 со стороны модели** (один `Post` на хранимый пост для всех лент, `View.entry`):
  `--ui qt --hours 2` USS 401,0 → 399,5 МБ, после возврата памяти 245,3 → 245,0 МБ,
  объектов Python 228 169 → 222 232. Почти ничего: вес был не в объектах Post.
* **Картинки** (28 окт: строка статистики настоящего окна — USS 465–547 МБ, `qt.images_mb`
  127,9 на 174 картинки, 3342 виджета; стенд ничего этого не видел — его адреса никуда не
  вели). С картинками на диске (`--ui qt --posts 4000 --hours 4`), после возврата памяти:

  | `media.image_cache_mb` | до возврата | после |
  |---|---|---|
  | 128 (прежнее по умолчанию) | 600,1 | 378,4 |
  | 64 | 570,7 | 318,8 |
  | 32 | 553,8 | 318,8 |

  Ниже 64 больше не уходит: картинки на экране держат их карточки, каков бы ни был кэш.
  По умолчанию теперь 64 МБ (шаг 6) — 60 МБ из 380, что держит открытое окно.
* **Аватарки разжимаются под свою рамку** (`images.face`: вдвое больше рамки, не меньше
  64 px — раньше как картинки ленты, до 1200 px, аватарка 400 px целиком под кружок 40 px):
  после возврата памяти −3…−13 МБ (по два прогона, A/B). Пробовали и отказались: держать в
  кэше картинку карточки сразу в размере рамки вместо разжатой (каждая на экране лежала
  дважды) — +12…+23 МБ, измерено, так что не делаем. Стенд от прогона к прогону оставлял
  впереди разные ленты (1062 виджета или 1936, разница 20 МБ): теперь впереди всегда Home.
* **Сколько лент держать нарисованными** (`ui.keep_hidden_lanes`, 3, `common/lanekeep.py`, Qt
  и GTK; GTK теперь соблюдает и `unload_hidden_minutes`): каждая открытая лента держала свои
  карточки 10 минут — нарисованная лента весит около 18 МБ (окно с одним Home — 175 МБ, все
  ленты открыты — 500 МБ после возврата памяти). Теперь держат только 3 открытые последними;
  открытая раньше отпускает сразу, как вперёд выходит другая. Все ленты открыты, 4000
  постов: 573 → 405 МБ до возврата памяти, 319 → 298 после; второй проход по ним ничего не
  добавляет (2255 виджетов в обоих случаях). Стенд после каждой ленты удаляет отпущенные
  виджеты, как это делает работающее окно (раньше он считал 10 147 виджетов, которые лишь
  ждали удаления).
* **Шаг 5 в Qt: только карточки у экрана** (`qt/feedview.py`, 29.10). Каждая карточка — это
  набор виджетов, а лента строила их по 40 сразу и держала до 120. Теперь в теле есть место
  для каждого поста (его высота — измеренная, когда он был построен, иначе средняя), а виджеты
  — только в пределах экрана выше и ниже. Не делегат, рисующий карточки: карточки на экране —
  те же виджеты, что и раньше (ссылки, выделение, меню, экранный диктор — как были), — важно
  было, сколько их существует. 4000 постов, открыты все ленты:

  | | до | после |
  |---|---|---|
  | USS, МБ | 405 | 263 |
  | после возврата памяти, МБ | 298 | 244 |
  | виджетов | 2255 | 1252 |
  | картинок в памяти, МБ | 64 | 33 |
  | окно открыто, Дом нарисован, мс | 1860 | 767 |
  | открыть все ленты (19), мс | 11 306 | 2651 |
  | самая медленная лента, мс | 1355 | 313 |

  `reading.build_at_once` больше нет (если он ещё в конфиге — так и будет сказано). Бюджеты
  (`tests/test_budgets.py`) опустились вместе с этим.
* **Карточки строятся по нескольку; память отдаётся сразу** (29.10, отчёт автора). В логе
  окна шесть подвисаний по 300–430 мс: пять — открытие ленты или далёкий прыжок, когда
  строились разом карточки на экран выше и ниже (`card.__init__`, `_measure`), одно —
  перерисовка ленты, искавшая свои посты по одному. Теперь карточки на экране строятся
  сразу, остальные — по `SLICE_MS` (8 мс) между делами окна, ближние первыми
  (`FeedView._build_more`); список постов в ядро — один запрос (`View._in`). Стенд, 4000
  постов, открытие лент: `_lay_out` максимум 210 → 110 мс, задержек больше 100 мс 13 → 1.
  Одна карточка здесь — ~6 мс одного `QLayout.activate` (её настоящая высота): порция
  вмещает хотя бы одну. А `smem` сразу после пролистывания лент показал 145 → 387 МБ, где
  освобождённое ещё не отдано (отсчёт статистики через 5 минут вернул 81 МБ):
  `diag.trim_soon` возвращает память через 5 с после того, как карточки отпущены
  (пролистаны, лента выгружена), одним потоком, без прохода gc.
* **Шаги 2–4 замерены заново, на 10 000 постов** (29.10): ядро без окна, сутки опроса:
  USS 55 МБ при 2000 постов, 82 МБ при 10 000 — но в том же процессе живёт поддельный
  сервер стенда (его 13 000 статусов словарями), и `--trace` считал его в «fedtail,
  остальное» (его файл — `fedtail/tests/fakes.py`: исправлено, группы стенда теперь
  сперва смотрят на `tests/`). Собственные объекты ядра при 10 000 постов — около 8 МБ.
  Шаги 2–4 остаются отложенными: окно ленты в ядре выиграло бы единицы мегабайт; вес
  телефона — его интерпретатор и `requests`, а не посты.
* **Карточка мерится один раз, а не три** (Qt, 29.10): сразу после показа Qt просил
  карточку разложиться заново, и наблюдатель мерил её снова — 9185 замеров на 2962
  карточки. Теперь этот запрос обслуживается при постройке, до наблюдателя; второй
  взгляд находит высоту в кэше (медиана замера 2,1 → 0,9 мс, замеров из цикла событий
  7028 → 3878).
* **langdetect** (`core/langs.py`, `core/atoms.py`, 30.10). Ядро отдельно на 2000 постов
  весило на этой машине 110 МБ, из них 57 — 55 профилей langdetect: список из 55 питоновых
  float на каждую из 87 000 n-грамм. Грузились они без фильтра языков и без правила, которое
  спрашивает: каждая строка Активности считала все атомы своего поста, угадывая и язык
  (`event_facts` теперь берёт потребности правила) — 110 → 52 МБ. Когда догадка нужна,
  читаются только латинские и кириллические профили (остальные письменности узнаются по
  буквам; `lanes.detect_among = "all"` — все), числами по 4 байта: 60 → 11 МБ, ответы те же.
  Бюджет ядра 75 → 65 МБ.
* **Наполнение новой ленты** (`store.link_items`, `core/custom.py`, 29.10). Где было тяжело
  самому ядру: свободная лента (и «Неразобранное») берёт посты своих источников, уже
  сохранённые, и записывала их обратно через `put_items` — каждый сериализовался заново, его
  сохранённый текст читался для сравнения, а наполнение держало до 3000 разобранных постов на
  источник — пик 25 МБ в Python, который процесс потом так и держал. Теперь привязываются
  только элементы, по id. 4000 постов, ядро отдельно: 89,5 → 72,5 МБ, раунд после новой ленты
  83 → 63 МБ; правила всех лент заново ~1000 → 700 мс; окно Qt 274 → 267 МБ. Сперва мерили не
  так: под `tracemalloc` ядро выглядело на 120 МБ, из них 55 МБ «вне Python» — это учёт самой
  трассировки; смотреть надо на числа без неё.
* **Стенд и отложенное удаление**: `processEvents()` никогда не удаляет то, что отпущено через
  `deleteLater()`, поэтому карточки, отпущенные при опросе и прокрутке, оставались в счёте
  (305 карточек живы, 48 показаны: 6299 виджетов, 393 МБ на 4000 постов); `membench.pump()`
  теперь делает то, что делает работающий цикл, везде, где стенд даёт окну поработать
  (1077 виджетов). В `qt_bench.py` та же дыра была до 30.10: после его прокруток удаления
  ждали 57 000 виджетов, и первая же пробная тема платила за все — 30–170 с; это выглядело
  как медленная тема (nord), а бисекция вела к карточкам возле экрана (f2a579a3). Теперь
  каждый его шаг сбрасывает удаления: тема — 1,1 с, худший кадр прокрутки 80 → 34 мс.
* **Шаги 2–4, сперва измерены**: ядро отдельно на 2000 постов — 61 МБ, из них 33 МБ — импорты;
  шаги 2–4 могут отыграть из этого самое большее около 25 МБ; основная масса — окно (220 МБ:
  виджеты, шрифты, картинки). Отложены, пока профиль настоящего, долго работающего окна не
  покажет, что доля ядра выросла.
* **Шаг 7, импорты измерены**: импорты ядра — 33 МБ: 15 — сам интерпретатор, 13 — `requests`
  (OpenSSL, urllib3), нужный, как только ядро подключается; ничего тяжёлого, кроме этого, при
  старте не импортируется. Ленивым импортам в ядре отыгрывать нечего; на шаге 7 осталось
  только начало работы окна.
