# Как облегчить fedtail

Статус: **шаг 0 (стенд) сделан**, базовая линия ниже; 28 окт 2026. План — автора.

## Зачем

Замер на ноутбуке автора (Qt на KDE, `python3 -m fedtail`, открыт долго): USS 484 МБ,
PSS 516 МБ, RSS 656 МБ. Это не утечка — ночная самопроверка растёт меньше чем на 10 МБ за
ночь, — это штатный объём собственных данных fedtail, так что худеть надо архитектурно.
Переписывать на другой язык не будем: чистый интерпретатор с PySide6 — 100–150 МБ, остальное
наше.

Цель: **150–250 МБ USS** в том же сценарии и заметно более шустрая лента.

## Принципы

* Один системный подход для всего кода и всех интерфейсов (Qt, GTK, терминал, веб,
  Android) — никаких правок под одну платформу.
* Ядро решает, что лежит в памяти; интерфейс получает только то, что видно.
* Сначала замер, потом правки; каждая правка подтверждается цифрами стенда.
* Пачками: CI не гонять после каждой правки; для проверки автором — пуш с `[skip ci]` и
  явное «делай pull».
* Релиз — только по слову автора.
* Доки разработчика — сразу на двух языках; список фич и справочник опций — тоже.

## Шаги

| шаг | что | статус |
|---|---|---|
| 0 | **Стенд**: синтетические сутки — 10 000 постов, 20 лент по правилам, картинки, сутки опроса; память по частям (посты, ленты, кэш картинок, виджеты интерфейса, модули; C++-часть Qt — через размеры кэшей и число объектов, tracemalloc её не видит); тайминги — холодный старт до первой ленты, открытие ленты, прокрутка 1000 постов, применение правил лент; в dev-сборке эти цифры в логе каждые несколько минут; цифры первого прогона — здесь, как базовая линия | сделан: базовая линия ниже |
| 1 | **Единый склад постов**: одна identity map в ядре — один объект на пост на всю программу; ленты хранят id и порядок, без копий постов; то же для аккаунтов, вложений, тредов | сделан: `Store._parse` — один `Stored` (только для чтения) на пост, пока его кто-то держит (слабо), общий для всех лент; `View.entry` — один `Post` на хранимый пост (аккаунты и вложения — внутри них) |
| 2 | **Компактные объекты вместо сырого JSON**: JSON сервера — только в SQLite; в памяти лёгкие структуры с полями для показа (`__slots__` или msgspec Struct, если пакет есть в Debian); разбор в `protocols/` сразу в них; повторяющиеся строки (URL аккаунтов, серверы, коды языков) интернировать | — |
| 3 | **Ленты считает база**: правила лент компилируются в SQL (WHERE + ORDER + LIMIT) с нужными индексами, вместо загрузки постов в Python для фильтрации; атомы, которые SQL не выразит, считаются при сохранении поста и хранятся колонками (язык, тип события, мой или чужой, уже видел…); EXPLAIN QUERY PLAN проверен для всех наборов лент; бюджет базы около 1 ГБ текста в год соблюдается | — |
| 4 | **В памяти только видимое**: «окно ленты» в ядре — интерфейс просит диапазон вокруг курсора (скажем, 50 постов), ядро отдаёт и держит небольшой буфер вокруг; неоткрытые ленты не загружены; счётчики непрочитанного — COUNT в базе; «где остановился» — курсор в базе, а не загруженная лента; один API для всех интерфейсов и Android | — |
| 5 | **Интерфейсы без виджета на пост**: Qt — QListView / QAbstractListModel и рисующий делегат; GTK — Gtk.ListView с моделью и переиспользуемыми строками; веб, терминал, Android — то же окно, дорисовка при прокрутке; высоты строк кэшируются, раскладка текста без нужды не пересчитывается | — |
| 6 | **Картинки и медиа**: декодируются сразу в размер показа (Qt: QImageReader.setScaledSize), полный размер — только при открытии; один кэш картинок с лимитом в МБ (опция, разумное значение по умолчанию), LRU; миниатюры кэшируются на диск; медиа вне экрана не декодируются; видео — по-прежнему только превью | частично: `media.image_cache_mb` (64 МБ по умолчанию с 0.22, измерено), `image_disk_mb`, `image_decode` |
| 7 | **Ленивый старт**: тяжёлые модули (определение языка, орфография, звук, всё редкое) — при первом использовании; первой рисуется заглушка с опоссумом, потом открытая лента, остальное в фоне; всё тяжёлое (разбор, запросы, определение языка, правила лент) — вне GUI-потока | частично: заглушка первой (0.22) |
| 8 | **Бюджеты как тесты**: стенд шага 0 — тест с потолками памяти и времени (старт, открытие ленты, прокрутка); превышение — тест падает, чтобы лёгкость не расползлась обратно с новыми фичами; гонять в полном CI, не на каждую мелочь | — |
| 9 | **Только если 1–8 мало**: горячие вычислительные куски по профилю — на Rust через PyO3, не трогая архитектуру ядра и интерфейсов | — |

Порядок: 0 → 1 → … → 8, после каждого шага — стенд и сравнение с базовой линией ниже; после
всего — проверка, что интерфейсы на всех платформах не разошлись (`tools/parity.py`,
`tools/behaviour.py`).

## Стенд

`tools/membench.py` — без сети, ваше ничего не трогает:

```sh
python3 tools/membench.py                  # ядро и общий слой
python3 tools/membench.py --ui qt          # и окно Qt (offscreen)
python3 tools/membench.py --trace          # где память Python, по пакетам (медленнее)
python3 tools/membench.py --json out.json --md out.md
```

Сценарий: поддельный сервер (`tests/fakes.py`) с `--posts` постами в Home (картинка в каждом
четвёртом, ответы, упоминания, Local тоже наполнена, лайки и подписки для Активности), база
заполнена как после нескольких дней опроса, свой набор лент fedtail плюс свои ленты до
`--lanes`, новый старт над этой базой, потом `--hours` опроса, по дюжине новых постов каждые
пять минут.

Что говорит: USS / PSS / RSS (`/proc/self/smaps_rollup`), с `--trace` — доля Python по пакетам;
счётчики ядра (`Core.diag_stats`); с `--ui qt` — число виджетов и кэш картинок (`--ui qt`
сперва кладёт в дисковый кэш настоящий JPEG каждой картинки и аватарки поддельного сервера, как
после нескольких дней чтения, — окно разжимает и держит их, как в жизни; `--image-mb N` задаёт
`media.image_cache_mb`). Время: холодный
старт (ядро, подключение, первый круг), первая лента, открытие всех лент и самая медленная из
них, правила заново, сутки опроса, и с `--ui qt` — прокрутка Home на 1000 постов.

Dev-сборка пишет USS и PSS в лог с каждой строкой статистики (`diag.smaps`, каждые
`debug.stats_minutes`).

## Базовая линия

Первый полный прогон, 28 окт 2026 (`python3 tools/membench.py --ui qt`: 10 000 постов, 20 лент,
из них видно 19, 24 ч; Python 3.13, два ядра облака, Qt offscreen; ни одна картинка не
скачалась — адреса поддельного сервера никуда не ведут, — так что кэш картинок здесь пуст):

| память | МБ |
|---|---|
| USS | 453,3 |
| PSS | 483,8 |
| RSS | 516,3 |

На ноутбуке автора было USS 484 МБ: стенд повторяет беду и без картинок — она в наших
структурах, а не только в изображениях (картинки появились на стенде позже — см. ниже: их доля
тоже велика).

| время | мс |
|---|---|
| холодный старт: ядро, подключение, первый круг | 1935 |
| первая лента (Дом) собрана | 49 |
| окно Qt открыто, Дом нарисован | 2113 |
| открыть все ленты (19) | 12 689 |
| самая медленная лента | 1819 |
| правила лент заново | 1319 |
| сутки опроса (288 кругов) | 195 679 |
| прокрутка Дома на 1000 постов | 396 |

Счётчики в конце: 13 457 статусов и 15 656 элементов в базе (32,6 МБ на диске), 294 031
объект Python (gc), 518 модулей, **14 497 виджетов Qt** — цель шага 5; каждая лента держит
свою разобранную копию каждого своего поста (`Core.lane_entries` → `json.loads` на ленту) —
цель шага 1.

Что говорят цифры, три прогона спустя (28 окт):

* **Собственные объекты Python — малая часть.** С `--trace` (2 ч опроса) tracemalloc видит
  около 95 МБ выделений Python при USS 517 МБ: ядро 18, питоновская часть слоя Qt 20, общий
  слой 4,5, json и прочее — остальное. Основное — C++-сторона Qt: виджеты, раскладка их
  текста и стили.
* **Освобождённая память остаётся в процессе, пока её не вернуть.** `--ui qt --hours 2`:
  USS 349 МБ после обхода всех лент; скрытые ленты выгружены (как делает
  `ui.unload_hidden_minutes` через 10 минут) — 854 виджета из 9382, а всё те же 349 МБ;
  после `malloc_trim(0)` из glibc — **193,5 МБ**. Работающий fedtail возвращает память каждые
  `debug.stats_minutes` (`diag.trim_memory`), так что с жизнью сравнивать надо последнее
  число; стенд печатает все три.
* **Шаг 1 на одном ядре** (`--hours 2`, без окна): USS 110,3 → 102,5 МБ, открыть все ленты
  656 → 362 мс, два часа опроса 9,2 → 5,4 с (ни одна лента не разбирает пост, уже разобранный
  другой).

Так что для ядра порядок плана верен, а вес окна — в карточках (шаг 5): каждая карточка —
десятки виджетов.

* **Шаг 1 со стороны модели** (один `Post` на хранимый пост для всех лент, `View.entry`):
  `--ui qt --hours 2` USS 401,0 → 399,5 МБ, после возврата памяти 245,3 → 245,0 МБ,
  объектов Python 228 169 → 222 232. Почти ничего: вес был не в объектах Post.
* **Картинки** (28 окт: строка статистики настоящего окна — USS 465–547 МБ, `qt.images_mb`
  127,9 на 174 картинки, 3342 виджета; стенд ничего этого не видел — его адреса никуда не
  вели). С картинками на диске (`--ui qt --posts 4000 --hours 4`), после возврата памяти:

  | `media.image_cache_mb` | до возврата | после |
  |---|---|---|
  | 128 (прежнее по умолчанию) | 600,1 | 378,4 |
  | 64 | 570,7 | 318,8 |
  | 32 | 553,8 | 318,8 |

  Ниже 64 больше не уходит: картинки на экране держат их карточки, каков бы ни был кэш.
  По умолчанию теперь 64 МБ (шаг 6) — 60 МБ из 380, что держит открытое окно.
